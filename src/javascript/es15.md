## Object.groupBy() / Map.groupBy()

按 key 分组，不用再手写 `reduce` 了。

````javascript
const items = [
  { name: 'a', type: 'fruit' },
  { name: 'b', type: 'veg' },
  { name: 'c', type: 'fruit' },
]

Object.groupBy(items, i => i.type)
// { fruit: [a, c], veg: [b] }
````

`Map.groupBy` 干的是一样的事，只是返回 `Map` —— 于是 key 就不限于字符串了，对象、数字都行。

````javascript
Map.groupBy(items, i => i.type).get('fruit')
// [{ name: 'a', … }, { name: 'c', … }]
````

## Promise.withResolvers()

一次拿到 promise 和它的 `resolve` / `reject`。

````javascript
const { promise, resolve, reject } = Promise.withResolvers()

setTimeout(() => resolve('done'), 100)
await promise    // 'done'
````

以前得这么绕：

````javascript
let resolve, reject
const promise = new Promise((res, rej) => {
  resolve = res
  reject = rej
})
````

典型场景是"Promise 需要在别的地方才被 resolve" —— 事件回调、任务队列、连接池。

## isWellFormed() / toWellFormed()

检测并修复孤立代理项，就是 `\uD800` 那种非法 UTF-16。

````javascript
'abc'.isWellFormed()       // true
'a\uD800'.isWellFormed()   // false

'a\uD800'.toWellFormed()   // 'a�'  ← 换成 U+FFFD
````

以前只能在编码那一步炸掉：

````javascript
encodeURIComponent('\uD800')
// URIError: URI malformed

encodeURIComponent('a\uD800'.toWellFormed())
// 'a%EF%BF%BD'
````

处理外部输入（URL、文件名、用户粘贴的文本）时先过一遍 `toWellFormed()`，能省掉一堆莫名其妙的报错。

## 正则 v 标志

`u` 标志的超集，主要加了**集合运算**和**多码位匹配**。

````javascript
/[\p{Letter}--[a-z]]/v.test('A')        // true   差集
'abcdef'.match(/[[a-z]&&[^aeiou]]/v)    // ['b']  交集
'abcdef'.match(/[[a-z]--[aeiou]]/v)     // ['b']  嵌套类做差集
````

还有两个新写法：

````javascript
/[\q{abc}]/v.test('abc')      // true   \q{} 把整个字符串当成一个元素
/\p{RGI_Emoji}/v.test('👨‍👩‍👧')  // true   能匹配多码位序列
````

上面这些在 `u` 标志下**全部报语法错误**。

> 语法上有个坑：**范围不能直接参与集合运算**。
> `[a-z&&[^aeiou]]` 会报 `Invalid set operation in character class`，
> 得写成 `[[a-z]&&[^aeiou]]`，把范围包进嵌套类。

## 可调整大小的 ArrayBuffer

新建时给个上限，之后可以长大、缩小。

````javascript
const buf = new ArrayBuffer(8, { maxByteLength: 16 })

buf.byteLength      // 8
buf.resizable       // true
buf.maxByteLength   // 16

buf.resize(12)      // 12
buf.resize(32)      // RangeError: Invalid length parameter
````

超上限直接抛 `RangeError`，不会悄悄截断。`SharedArrayBuffer` 也有对应的可增长版本。

## ArrayBuffer 的所有权转移

把 buffer 转手，原来那个直接作废 —— 不用再靠 `postMessage` 才能"分离"了。

````javascript
const b1 = new ArrayBuffer(8)
new Uint8Array(b1).set([1, 2, 3, 4, 5, 6, 7, 8])

const b2 = b1.transfer(4)

b1.byteLength       // 0
b1.detached         // true
new Uint8Array(b1)  // TypeError: 不能在已分离的 ArrayBuffer 上构造
[...new Uint8Array(b2)]   // [1, 2, 3, 4]
````

`transfer` 和 `transferToFixedLength` 就差在一点：

| 方法 | 结果还能 resize 吗 |
|------|------------------|
| `transfer(n)` | 保留（原来可调整就还可以） |
| `transferToFixedLength(n)` | 不能，固定长度 |

## Atomics.waitAsync()

`Atomics.wait()` 的异步版。同步那个会**阻塞线程**，只能在工作线程里用；这个返回 Promise，主线程也能等。

````javascript
const sab = new SharedArrayBuffer(4)
const i32 = new Int32Array(sab)

const r = Atomics.waitAsync(i32, 0, 0)
if (r.async) {
  await r.value    // notify 之后拿到 'ok'
}
````

返回形态有两种，看它到底等没等：

````javascript
Atomics.waitAsync(i32, 0, 999)
// { async: false, value: 'not-equal' }  ← 期望值对不上，立即返回

Atomics.waitAsync(i32, 0, 0)
// { async: true, value: Promise }       ← 真的在等
````

`SharedArrayBuffer` / `Atomics` 这套东西日常业务基本碰不到，主要是多线程计算和 WebAssembly 在用。
